### Detailed recommendations

#### #1 — Generate the Bridge API table from the router

**What**: Replace the hand-written table in `README.md` §"Bridge API" with a
generated one.

**How**:
1. Add `<!-- routes:start -->` / `<!-- routes:end -->` markers around the table.
2. Create `scripts/gen-routes.mjs`. The bridge's dispatch is a flat
   `if (path === "…" && req.method === "…")` chain in
   `whatsapp-bridge/src/server.js`, so extraction is a regex over that one file
   — no framework introspection needed:
   ```js
   const src = await readFile("whatsapp-bridge/src/server.js", "utf8");
   const routes = [...src.matchAll(/path === "([^"]+)"[\s\S]{0,120}?req\.method === "(\w+)"/g)]
     .map(([, path, method]) => ({ path, method }));
   ```
   Note: `server.js` contains a NUL byte, so any shell-side grep needs `grep -a`.
   Reading it in Node avoids the issue entirely.
3. Add `"docs:check": "node scripts/gen-routes.mjs --check"` to `package.json`,
   exiting non-zero when the generated table differs from the committed one.

**What it replaces**: `README.md` §"Bridge API", the 33-row table.

**Drift risk if not automated**: Demonstrated — 14 routes drifted within two
days of the table being written.

#### #2 — Generate the tool inventory from `agent/tools/`

**What**: Both `README.md` and `SPEC.md` enumerate agent tools by hand. Each
tool is a `defineTool({ description, inputSchema })` in its own file, so the
inventory is mechanically derivable and the descriptions are already written.

**How**: `scripts/gen-tools.mjs` imports each `agent/tools/*.ts`, reads
`.description`, emits a markdown table between markers in both files. Fail CI on
diff. This alone would have caught both phantom tools and all 14 omissions.

**Drift risk if not automated**: An agent spec naming tools that do not exist is
a correctness problem, not a cosmetic one — it is exactly the class of error
CLAUDE.md's PALS's Law section is about.

#### #3 — Check `.env.example` against actual config reads

**What**: A test, not a generator — the file's prose comments are its real value
and must not be machine-overwritten.

**How**: `scripts/check-env.mjs` collects every `process.env.X`, `env.X` on an
env-typed parameter, and Go `os.Getenv("X")`, subtracts a small allowlist of
system vars (`TMPDIR`, `PORT`, `NODE_ENV`), and asserts each remaining key
appears in `.env.example`. Wire it into `node --test` so it runs with the
existing 899-test suite and needs no new infrastructure.

**Note on method**: the naive `process.env.X` grep produces false positives here
— this codebase overwhelmingly passes `env` as a parameter defaulting to
`process.env` (`parseAllowlist(env = process.env)`), so a `process.env`-only
scan reports ~20 phantom keys that are all real. Match on the literal key name
across all sources instead. That mistake is reproduced and corrected in this
report's own methodology.
